Databases

Databases, registries and projects

Register a database once and you type its name from then on. This is where that name is looked up — and what happens on a machine where two registries both hold it.

sloop never asks for a connection twice. You register a database — a name, a connection and where its password comes from — and every command after that takes the name. sloop backup shop, sloop restore shop, sloop query shop.

The set of databases sloop knows is a registry. There is one global registry per machine and as many project registries as you make, which is what the second half of this page is about.

Registering one

Two ways, and they produce the same record. Give the whole connection as a URL, or give the fields one at a time — useful when a password manager holds the pieces separately, or when a host name has a character you would rather not escape.

--test is the reason the engine line comes first: it opens the connection before saving anything and refuses to save a record that does not work. Without it the record is written as given and the first backup is where you find out.

The name is yours — ledger above is filed under that name while the database on the server is also called ledger, and neither has to match the other. Renaming says what happens when they stop matching.

The password is asked for on a terminal and never appears in the command. It is not in argv, so it is not in ps, and it is not in the registry either — only the route to it is. That is the next section.

It does not guess, and it does not prompt for the connection

With neither --engine nor --url, db add stops and names both. The menu asks those questions; the command does not, because a command that prompts is a command that hangs in a scheduled run.

MySQL and MariaDB

The same command, a different scheme. postgres, mysql and mariadb are the three sloop speaks, and MariaDB is its own engine rather than a MySQL setting because it ships mariadb-dump where MySQL ships mysqldump.

over TLS is not something sloop turned on. It reports what the connection actually negotiated, and it says not encrypted just as plainly when that is the truth — which is what the PostgreSQL blocks above say.

Where the password lives

A registry holds a route, never a value. There is no spelling of a password a registry will accept, which is what makes it impossible to put one there by accident. Four routes, one flag each:

FlagWhere it livesFor
--keyringthe Secret Servicethe default, and what you want unless something below applies
--encrypted-fileXChaCha20-Poly1305, key from Argon2ida headless machine with no keyring running
--env <VARIABLE>an environment variable, read every runautomation, and CI in particular
--password-from <COMMAND>whatever that command printsa team password manager

Both notes are the point rather than a warning to fix. A variable that is not set yet and a command that is not installed yet are both fine at registration time, because neither is read until the run that needs it — so SHOP_PASSWORD=… sloop backup nightly works on a machine where nothing was stored.

db list shows every record and the route beside it. It is the one command here you can run with somebody watching:

Nothing on that listing is a password. Not one of those phrases can be one — the registry stores which of the four routes to take, and the value is fetched at the moment it is needed and handed to the client through a pipe. It never reaches argv, so it never reaches ps.

Creating one, rather than registering one

db create is for a database that does not exist yet. It makes the database and the role that owns it, grants that role what a backup needs, then registers the result — so the account sloop uses afterwards is one that was made for the job rather than the superuser you happened to have.

The superuser password is used once and kept nowhere. The new role's password is the one that gets stored, and sloop generates it when you do not supply one — so the credential sloop holds from then on is a credential nobody has ever seen in a shell.

Checking and changing what is registered

db test opens the connection and reports what answered — engine, version, and what is securing the link. With no name it does that for every registered database, which is the quickest way to find the one that broke.

A password route that cannot be followed fails here too, and fails loudly. A command that is not installed is not a connection problem, so the message names the command rather than the host:

db edit changes a field without re-registering. It prints the old connection and the new one, in that order, so what changed is visible rather than implied:

Renaming, and the name on the server

db rename changes the name sloop files it under. The database's own name on the server does not change, is not contacted, and does not need to match — they are two different names and sloop never conflates them.

Everything keyed to that database follows the rename: its backups move with it on disk, and its schedule and its activity history stay attached. The password does not move, because it is filed under the connection rather than the label — which is also why renaming does not make you type it again.

After that rename, db test accounts reports postgres://app@127.0.0.1:5442/ledger. That is not a mistake in the listing: accounts is what you type and ledger is what the server calls it.

Forgetting one, and destroying one

Two commands that sound similar and are not remotely the same. db remove forgets a record. db drop destroys a database on a server.

That third line is printed every time, before the question, because the difference is worth stating rather than assuming. Removing takes the password out of the Secret Service as well — a credential for a database sloop no longer knows about is a credential nobody is going to remember to delete.

db drop is the destructive one, and it is typed rather than clicked. What you type is the database's own name on the server, not the label — because the label is what sloop calls it and the name is what is about to stop existing.

Nothing is kept

db drop takes no safety copy. That was removed deliberately: a dump taken on the way past had no manifest, read as wreckage in backups list for ever, and could not be restored from. So the command says so before the question, while there is still time to run sloop backup instead.

Note the last line: dropping does not remove the record. The name stays registered and now points at nothing, and db remove is what forgets it. Two commands, two decisions.

From a scheduled run there is no terminal to type at, so it refuses — and --confirm is the only thing that answers it. --yes does not, and is not consulted:

--confirm has to match exactly, which is the property that makes it safe in a file: a scheduled line names the database it destroys and cannot be repointed at a different one by editing a single flag.

Registries, global and project

Everything above went into the global registry — one per machine, the one a bare name uses when nothing else applies. sloop init makes a project registry in a directory, and a project's databases belong to that directory rather than to the machine.

Two things that line records. The project has a name, taken from the directory, and that name reaches it from anywhere on the machine as sloop -C acme-api — so a scheduled backup does not have to know where the checkout is. And .sloop ignores itself, so a project registry inside a repository never shows up in git status.

Which registry a bare name means

Five rules, checked in order, and the first one that matches wins. This is the whole of it — there is no sixth case and no per-command exception.

  1. 1

    --global

    The global registry, full stop.

    Nothing else is consulted — not a project you are standing in, not the variable.

  2. 2

    -C <path|name>

    That project.

    A directory, or a name sloop init recorded. Works from anywhere on the machine.

  3. 3

    SLOOP_PROJECT

    The same thing, from the environment.

    -C outranks it when both are given, so a flag on the line always beats the shell it ran in.

  4. 4

    .sloop

    The nearest one at or above the working directory.

    The way git finds .git — walk up until a .sloop turns up, and stop at the first.

  5. 5

    no flag, no variable, no .sloop

    Otherwise, the global registry.

    Which is where a machine with no projects on it lives all the time.

So a name registered in both belongs to the project, because rung four is reached before rung five. sloop does not leave that to be worked out — it says so in the listing and names the rung it took when it registers:

The global shop is still there, still backed up, still restorable — it is just not what a bare shop reaches while you are standing in this directory. Where the store lives

/home/you/.sloop — the same path on all three platforms, spelled the way each one spells it. A store left behind in an older location is moved there once rather than ignored, so an upgrade does not quietly strand a registry.

A project's store is .sloop inside the project directory: /home/you/projects/acme-api/.sloop for the one above.

The registry is a database, not a file

It lives in the PostgreSQL that sloop setup prepares — sloop's own, on its own port, holding the registry, the schedules and what the background service has seen. You can open it yourself, and sloop tells you how:

Nothing about that is sealed. It is an ordinary PostgreSQL on an ordinary port, and psql, DataGrip or anything else that speaks the protocol will read it — and it still holds no passwords, only the four routes to them, for exactly the reason the listing further up holds none.
