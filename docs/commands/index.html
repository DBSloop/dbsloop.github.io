The global flags

These eleven work on every command, and they are not repeated in the tables further down — each command's table lists only what is its own. They are the ones every command has, worked out by intersection rather than kept in a list, so a flag that stopped being global would leave this section on its own.

FlagWhat it does
--globalUse the global registry, whichever directory you are standing in
-C, --project <PATH|NAME>Work on this project: a directory, or a name sloop init recorded
--password-command <COMMAND>Take the password from this command's output instead of wherever the registry says
-y, --yesAnswer yes to a question this would otherwise stop and ask
--forceOverride a refusal that is there to protect something
--confirm <NAME>The name of the thing being destroyed, typed out
-q, --quietSay nothing but what went wrong
--jsonPrint one JSON document instead of talking
--no-colorNever colour the output, whatever this terminal supports
--log-file <PATH>Append everything this run prints to a file as well
--dry-runSay what would happen and change nothing

Why --yes, --force and --confirm are three things

They look interchangeable and are not, and reaching for the wrong one is how an automated run either stops when it should not have or destroys something it should not have.

  • --yes answers a question. A command that would stop and ask something proceeds. It is never enough to destroy a named thing, and it is never a way past a refusal.
  • --force overrides a refusal. A refusal is sloop declining to do something because of what it found — a circular foreign key, a source that is also the destination. It answers no questions, and the refusal that can be overridden says so when it fires.
  • --confirm <NAME> types the name out. It is the only way to run a destructive command with no terminal, and it has to match exactly — so a scheduled line names the thing it destroys and cannot be repointed at something else by editing one flag.

With no terminal to ask at, sloop never prompts. It exits 2 and names the exact flag that would have answered the question, which is why a scheduled run can fail but cannot hang. Automation has the exit codes and the rest of it.

Getting set up

Preparing a machine, and a project registry in a directory.

sloop setup

Prepare the PostgreSQL 18 sloop keeps its own state in.

Runs on a machine that has not been set up, and is safe to run again on one that has. A PostgreSQL 18 already serving on 5432 is used as it stands; anything else gets a cluster of sloop's own on 5433, which disturbs nothing already on the machine.

sloop setup [OPTIONS]

FlagWhat it does
--superuser-password-command <COMMAND>A command that prints the superuser password of the PostgreSQL already on this machine, for a run with no terminal to ask at
--superuser-password-stdinRead that password from standard input instead of asking for it
--db-password-command <COMMAND>A command that prints the password to give sloop's own database user
--db-password-stdinRead that password from standard input instead of generating one

sloop init

Start a project registry in this directory, or in the one -C names

sloop init [OPTIONS]

Takes no flags of its own — only the 11 global ones above.

Reading

Looking inside a database without writing SQL.

sloop query

Read a database without writing SQL.

Pick a table, tick the columns, choose the test — everything comes off a list and the only thing you type is the value you are looking for. The results open in a grid you can scroll, two hundred rows at a time.

Everything it runs, including --sql, runs inside a transaction the server has been told is read-only. Nothing this command sends can change anything, and it is the server that guarantees that rather than a list of forbidden words.

sloop query [OPTIONS] [NAME]

ArgumentWhat it is
[NAME]Which registered database. Left out, the ones sloop knows are listed
FlagWhat it does
--sql <STATEMENT>Run this one statement instead of building one

The background service

Registering sloop with the machine, and what it does once it is there.

sloop service

Keep sloop running in the background, so it works with nobody logged in.

Registers sloop with whatever this machine uses to run things at boot — systemd on Linux, launchd on macOS, the Service Control Manager on Windows. Once it is installed and started, it comes back by itself after a restart.

This is for a server, not for a laptop you are working on. On a machine you use yourself, running sloop backup when you want a backup is the simpler thing and nothing here improves on it.

It never opens a port. Nothing listens, nothing can be reached from the network, and what it records is read back with sloop service status from a file on this machine.

sloop service [OPTIONS] <COMMAND>

Subcommands: install, uninstall, attach, detach, start, stop, schedule, activity, status. Each has its own entry below.

Takes no flags of its own — only the 11 global ones above.

sloop service install

Register sloop with this machine, so it starts at boot.

Writes the unit, the agent or the service entry, whichever this platform uses, and starts it unless told not to. Needs administrator rights, because starting something at boot is a machine-wide change on all three platforms.

sloop service install [OPTIONS]

FlagWhat it does
--no-startRegister it, and leave it stopped
--user <USER>Run as this account instead of the one installing it. Linux and macOS only
--interval <SECONDS>Seconds between one round of readings and the next. 60 by default [default: 60]

sloop service uninstall

Stop the background service and take it off this machine, keeping what it recorded.

Stops it, removes the unit or the service entry, and removes the key file it reads its credentials with. Nothing sloop has recorded is deleted — attachments and history stay, so installing again picks up where this left off.

sloop service uninstall [OPTIONS]

Takes no flags of its own — only the 11 global ones above.

sloop service schedule

Back this database up on a schedule, with no cron line anywhere.

The service takes the backup, applies the retention policy and prunes what falls outside it. Nothing is written to crontab, Task Scheduler or systemd timers — the schedule is a row sloop's own database holds, and sloop service status says when each database last ran and when it runs next.

sloop service schedule [OPTIONS] <NAME>

ArgumentWhat it is
<NAME>The name it is registered under in the global registry. It has to be attached
FlagWhat it does
--every <INTERVAL>How often: 30m, 6h, 1d, 2w. The same spelling --older-than takes
--keep <COUNT>Keep this many of the newest backups, and prune the rest
--keep-for-days <DAYS>Prune anything older than this many days
--offStop backing it up. It stays attached and stays sampled

sloop service activity

What the service has recorded: rows in, rows out and size, by day, week and month.

Rows, not bytes. No engine reports bytes per database — PostgreSQL counts rows, MySQL's byte counters are server-wide — so what is shown is what is true, and every line says which it is. A period nothing was watching reads as having no readings rather than as a zero.

sloop service activity [OPTIONS]

Takes no flags of its own — only the 11 global ones above.

sloop service status

Is it installed, is it running, and when did it last do anything.

Answers honestly when it is stopped, and when it was never installed at all — the two are different states and a monitoring system needs them apart.

sloop service status [OPTIONS]

Takes no flags of its own — only the 11 global ones above.

This machine

The servers sloop installed, what it can check, and taking it all off.

sloop server

The database servers on this machine — installing one, listing them, and opening sloop's own.

install is engine, then version, then one confirmation, instead of finding the project's website and following its installation instructions: the archive is downloaded by the system's own curl, proved against whatever that project publishes to prove it with, and started on a port that collides with nothing already here. connection is the other direction — where sloop keeps its own state, so you can open it in psql or DataGrip yourself.

sloop server [OPTIONS] <COMMAND>

Subcommands: install, list, connection. Each has its own entry below.

Takes no flags of its own — only the 11 global ones above.

sloop server install

Download, install, configure and start a database server

sloop server install [OPTIONS] [ENGINE]

ArgumentWhat it is
[ENGINE]postgres, mysql or mariadb. Left out, it is asked for
FlagWhat it does
--version <VERSION>Which version, as the project writes it. Left out, the ones available are listed

sloop server list

Every server sloop has installed here, and how to reach each one

sloop server list [OPTIONS]

Takes no flags of its own — only the 11 global ones above.

sloop server connection

Where sloop keeps its own state, so you can open it yourself.

Host, port, database and user, ready to be pasted into psql, DataGrip or anything else that speaks PostgreSQL. The password is kept where this machine keeps secrets and printed only when it is asked for, on a terminal — never into a log file, a document or a pipe.

sloop server connection [OPTIONS]

FlagWhat it does
--show-passwordPrint the password too, not only where it is kept

FlagWhat it does

sloop reset

Put this machine back to the moment sloop was installed.

Removes sloop's own database and everything it knows. A PostgreSQL that sloop installed goes with it; one that was already here keeps every other database on it and loses only sloop's. sloop setup is needed again afterwards.

Backups are never deleted, by this or by uninstall.

sloop reset [OPTIONS]

Takes no flags of its own — only the 11 global ones above.

sloop uninstall
