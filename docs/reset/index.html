Reset and uninstall

Put the machine back to the moment sloop was installed — and the one thing that can still be lost when you do.

Two commands, and the second is the first plus the binary. They share one implementation, so they can never drift into destroying different things.

Backups are never deleted. Not by reset, not by uninstall, not ever. A registry is a minute of typing and a PostgreSQL is a download; a dump that is gone is gone.

It asks for an administrator at the door

A reset takes the background service off the machine, and changing what a machine runs at boot needs more than an ordinary account. So that is the first thing either command checks — before the survey, before the list, before the name is typed — and a run that cannot do it stops while the machine is still whole rather than deleting the cluster and then discovering it cannot finish.

Run it again from sudo and it carries on. Only a machine with a service registered needs this: there is nothing else in a reset that an ordinary account cannot do, because everything else sloop put here went under your own profile in the first place.

What goes, and what stays

sloop reset surveys the machine before it does anything to it, and prints both columns. The last thing you read before a database stops existing should be a list of what is going, not a yes-or-no.

This will remove

  • sloop_database

    The registry, the schedules, the service’s readings and the vault. All of it.

  • sloop_db_admin

    The role that owned it, dropped in the same run.

  • server.toml

    The record that said which PostgreSQL was sloop’s, and on what port.

  • projects/ and locks/

    Where projects were registered, and any lockfile left behind by a run.

  • The PostgreSQL — sometimes

    Only if sloop installed it. The next section is the whole of that question.

  • The background service

    Taken off the machine before anything else goes, because it wakes on a timer and opens the store every round.

  • Every server sloop installed

    Each one stopped first, then its directory — a running server holds its own files open, on Windows especially.

  • Every password sloop filed

    Its own superuser and role, the servers it installed, your registered databases and the SSH passphrases beside them — out of the keyring, out of the encrypted file.

This will keep

  • Every backup

    Not by reset, not by uninstall, not ever. They are the one thing here that cannot be made again.

  • Every other database

    On a PostgreSQL sloop did not install, only sloop’s own two objects go.

  • Every other role

    Two statements run, and both name something sloop created.

  • Your databases themselves

    Registering one never touched it, and forgetting all of them does not either.

  • Passwords sloop never held

    A ${VAR} route or a --password-command points at a secret somebody else keeps. There is no copy here to remove, and it says so rather than pretending.

One question decides how much goes

Who installed the PostgreSQL. sloop wrote the answer down at setup — origin in server.toml — and reset reads it rather than guessing.

origin = sloop

sloop downloaded it and installed it under ~/.sloop, so it is sloop's to take away. The cluster and its binaries go, in one directory. sloop setup downloads and installs again.

origin = machine

The PostgreSQL was already here and sloop was a guest on it. Two statements run — DROP DATABASE and DROP ROLE — and both name something sloop created. Not the server, not another database, not another role.

The name, typed out

This destroys a database. So it is the strongest form of the rule: sloop_database, typed out, or --confirm sloop_database for a run with nobody there. -y will not do it and --force will not do it.

The one thing that can still be lost

Backups survive reset. Being able to read them may not, and this is the whole reason the page exists.

An encrypted backup is readable only with its private key. On a machine with a working keyring that key lives in the keyring, which reset does not touch. But on a machine with no keyring — a headless Linux box — the key lives in the Argon2id vault, and the vault is inside sloop_database, which is precisely what reset destroys.

Run this before you run reset

sloop key export — and keep the line it prints somewhere sloop cannot reach. Without it, every encrypted backup this machine took becomes a file nobody can open. There is no recovery, no reset and nobody to ask.

Reset says so itself, in the block above, before the name is typed rather than after. It is the only warning on this page that describes something irreversible that reset does not do — it describes what you will have done by running it unprepared.

uninstall is reset plus the binary

Everything above, and then sloop itself: the directory the installer made and the PATH entry that points at it.

The open shell is the one thing it cannot fix. A shell read its environment when it started and keeps it; sloop will still resolve in the window you ran this in until you open a new one. It says so rather than leaving you to notice.

The PATH block comes out of every startup file that could be holding one — .bashrc, .bash_profile, .profile, .zshrc, .kshrc and fish's conf.d — not only the current shell's. Coming back

sloop setup, and the machine is ready again. What it cannot restore is what was in the database it destroyed: the registry, the schedules and the service's history are gone, and the databases they described have to be registered again.

The backups are still on disk with their manifests, so restoring one needs the database registered again and — if it was encrypted — the key you exported.
