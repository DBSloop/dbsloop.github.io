Reading a database

Pick a table, tick the columns, choose the test. No SQL — and nothing either form runs can write, because the server is what refuses it.

sloop query opens a database for reading. There are two ways in: a builder that asks questions, and --sql for one statement when you already know what you want. Neither can change anything, and the second half of this page is about why that is a guarantee rather than a promise.

The builder

sloop query shop with no other flags. Six questions, and the only thing you type is a value — every table, every column and every test is picked from a list the database itself supplied.

  1. 1

    Which database?

    Skipped when you named one on the command line. Otherwise every database this registry knows, as a list.

  2. 2

    Which table?

    The tables that are actually there, read from the catalogue. Not typed, so it cannot be mistyped.

  3. 3

    Which columns?

    A tick list of that table’s columns. Tick none and you get all of them.

  4. 4

    Narrow it down?

    No, and every row comes back. Yes, and it asks the next three — then offers another condition.

  5. 5

    Which column? / And it…

    The test, from a list of eleven: is, is not, contains, starts with, ends with, is more than, is less than, is at least, is at most, is empty, is not empty.

  6. 6

    What are you looking for?

    The only free text in the whole builder, and it is a value rather than a fragment of a statement. The tests that need no value — is empty, is not empty — skip it.

There is no DROP on any of those lists, so there is no DROP to catch. The builder is safe because of what it can produce, not because of what it screens out — and that is a different kind of safe from a filter.

The builder ends in a scrollable grid, two hundred rows at a time. The page is a LIMIT in the statement rather than a window over everything the server sent, so a table nobody could print is a table you can open and page through.

--sql, for one statement

The flag form exists for two reasons: somebody who knows SQL should not have to click through a builder to run one statement, and a session done by hand should become a line you can schedule.

--sqlprints rather than opening the grid, and the choice is made by which form you used rather than by guessing at what is attached — a flag form that opened a full-screen grid could not go in a script at all.

Nothing it runs can write, and the server is what says so

--sql takes any statement you give it. It is not checked against a list of forbidden words. Instead, every statement either form produces runs inside a transaction that sloop has told the server is read-only — and from there it is the engine's rule, not sloop's.

Read the error text: cannot execute UPDATE in a read-only transaction is PostgreSQL talking, not sloop. sloop did not inspect that statement, decide it was a write and block it. It handed it to the server inside a read-only transaction and the server refused it.

Where MySQL and MariaDB need one more thing

On PostgreSQL the guarantee is complete and it is entirely the server's. On the MySQL family it is not, and sloop is explicit about the difference rather than quietly papering over it.

A READ ONLY transaction on MySQL refuses every data change — including the hidden one above. It does not refuse DDL, because CREATE TABLE performs an implicit commit that ends the transaction before it runs. There is no session-level setting that closes that gap; read_only is a server-wide switch and belongs to the administrator. sloop only reads, and CREATE is not a statement that reads — sloop's words this time, and the hint says exactly why sloop had to be the one to say them. Two fences on those two engines, both needed, and the message tells you which one you hit.

What this is not

It is not a permission system. A read-only transaction stops the statement from writing; it does not stop the role from reading anything that role may read. If a database holds something a person should not see, that is a grant to get right, not a flag on this command.

The flags query takes are on the command reference, generated from --help.
