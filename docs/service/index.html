The background service

The background service

A nightly backup with a retention policy, and not a line of cron anywhere. sloop registers itself with the machine and does the work with nobody logged in.

Everything else in these docs is a command you type. This is the one that runs when you are not there — and it is not a wrapper around your scheduler. sloop registers itself with the machine's own service manager and does the work itself.

Showing Linux. What gets registered, and how you elevate, both change with it.

Nothing is written to crontab or a systemd timer. The service takes the backup itself and applies the retention policy itself — running the same backup and backups prune you would have typed, with --yes and never --force.

Elevation, before anything happens

On Linux sloop registers a systemd unit at /etc/systemd/system/sloop.service. Changing what a machine runs at boot needs an administrator, and sloop checks that before it does anything rather than failing halfway with a permission error:

Nothing has been changed by this run. That is the part worth trusting — the check happens first, so a refused run leaves the machine exactly as it was. To go ahead, run it with sudo and run sudo sloop service install.

Four commands need that. Five do not:

CommandWhat it doesNeeds elevation
service installregisters it with the machineyes
service uninstalltakes it off againyes
service startstarts it nowyes
service stopstops it nowyes
service attachwatch a databaseno
service detachstop watching oneno
service scheduleback one up on a scheduleno
service statusinstalled, running, last run, next runno
service activitywhat it has recordedno

install takes --no-start to register it and leave it stopped, --interval <SECONDS> for the gap between rounds of readings (60 by default), and --user <USER> to run as a particular account — Linux and macOS only, because a Windows service runs as LocalSystem.

Attaching a database

Installing the service does not make it watch anything. service attach does, and it is picked up without a restart:

The service only watches the global registry

A service has no working directory, so there is no project for it to be standing in. A database registered only in a project cannot be attached, and this is the first thing that goes wrong for somebody who put everything in one.

sloop db add <name> --global … is the fix, and which registry a bare name means is the page for why there are two.

Detaching stops the watching. It does not delete anything already recorded — and neither does service uninstall.

Scheduling a backup

Attached means sampled. Scheduled means backed up, and that is a second, separate step:

One line, and it carries both halves: --every 1d is how often, and --keep 7 --keep-for-days 30 is what survives. The retention is applied by the service after each run — and only after a backup that worked, so a failed night never prunes the copies that succeeded.

--every takes 30m, 6h, 1d, 2w — the same spelling backups prune --older-than takes.

--off stops the backups and leaves the database attached, so it keeps being sampled for activity. Attaching and scheduling are separate on purpose, and turning one off does not turn the other off.

A missed run, and a collision

A machine that was asleep for a week does not wake up owing you a hundred and sixty-eight backups. A missed run is caught up once and labelled late, and the next one is measured from now rather than from the schedule it fell off.

And if a scheduled run meets one you started by hand, the schedule stands aside: one lockfile per database, and the run that finds it held exits 7 having taken nothing. The manual run finishes untouched.

Checking on it

service status answers four questions: installed, running, last run, next run.

Every line of that is a fact rather than a guess — not picked up yet, never run, no service has ever read this list. On a machine where the service is installed and running, those become the times it actually ran and the time it runs next.

Activity and monitoring is the page for what those numbers are and, just as importantly, what sloop will not pretend to measure.

From nothing to a nightly backup

Four commands, and only the first needs an elevated terminal:

  1. sudo sloop service install — register it with the machine.
  2. sloop db add orders --global --url … — the service reads the global registry.
  3. sloop service attach orders — start watching it.
  4. sloop service schedule orders --every 1d --keep 7 --keep-for-days 30 — nightly, keeping a week, pruning after a month.

Then sloop service status whenever you want to know it is still true. Every flag any of these takes is on the command reference.
